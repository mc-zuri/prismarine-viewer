## Bedrock preview

Seven pages that show what the viewer draws of a Bedrock Edition version, with no server or world (the replay reads its recordings in the page, and the gameplay page runs a server of its own there):

* `gameplay.html`: the showcase world below, or a world recorded from a Bedrock server, played in first or third person in any version, or walked by clicks with a pathfinder: a Bedrock server running in the page (a Web Worker) sends it, and a client on the page plays it, the two exchanging the game's own packets over a MessagePort. Walk, sprint, sneak, jump and fly with the version's player physics, break and place blocks, open gates, walk to a block clicked on (mineflayer-pathfinder, its route drawn), and type commands; with the blob cache on or off and hashed block ids on or off (see [Gameplay](#gameplay))
* `world.html`: a small world of four biomes (plains, cherry grove, swamp, desert) with everything below together, and a tour of it: a house whose stairs roof turns its corners, fences and panes joining their neighbours, beds, banners, chests and heads shaped and coloured by their block entities, a farm, a waterfall and a pond, and villagers, a golem, animals, mobs and players moving about (walking, sneaking, swimming, gliding) with their names over them in the game's font; and the ender dragon sending fireballs at the ground, their breath trailing them and lingering where they land, and a skeleton shooting arrows (projectiles and particle effects)
* `replay.html`: a recording of a Bedrock client's packets played back: the world it was made in and its entities as the server told the client of them, with play, pause, speed and an entity for the camera to follow. The recordings are the `.proxy.bin` files of bedrock-observer and the proxy recorder (as they are, or gzipped: `.proxy.bin.gz`), with the `world.json` of their world beside them: those of `public/recordings` (a few of bedrock-observer's fixtures: entities in 1.16.201, 1.21.60 and 1.26.51, and the dimensions with the ender dragon), and those of a directory the server is started with (`node examples/bedrock_preview/server.js 3000 <directory>`). The page fetches a recording as a file and reads it in a Web Worker (`replay-worker.js`, `src/replay/decode.js`) with bedrock-protocol, as the gameplay page reads its packets, in the protocol of the version, else of the nearest version before or after it that reads its packets (a client build minecraft-data has no version of). `recording.js` reads them in Node the same way
* `blocks.html`: every block state of a version in a grid (or those whose name matches a filter), the camera turning around them so that every side shows, and water, flowing water, grass and leaves in several biomes, each tinted as its biome tints it
* `entities.html`: every entity of a version, in the poses and movements the game animates: standing, walking, sprinting, sneaking, swimming, gliding... With what they hold in either hand and wear (armour, shields, tridents: the version's attachables), their variants, flags and entity properties (a cow's climate), and the players' skin: Steve and Alex, or a skin image of your own. The particle effects they start show as their animations say: a blaze's flames (charged), an evoker's spell (casting), a phantom's wing dust, a bee's nectar (its `has_nectar` property)
* `particles.html`: every particle effect of a version (its resource packs' particles), listed with how it plays, and filtered by name; those chosen play side by side in a grid, each under its name: those that loop or run on run on, those that end play again every few seconds, and those whose particles the game emits itself (of a manual rate) are given some all the time. Their particles land on the ground. `particles.html?version=bedrock_1.26.51&filter=flame&play=shown` plays those of a filter (`play=all`: every effect, or identifiers comma separated)

* `items.html`: every item icon of a version as minecraft-assets exports it (`items_textures.json`), and each aux variant of an item beside it (a bed's colours, a potion's effects, a legacy block item's kinds), drawn as the viewer draws a dropped item and as the game shows it in the inventory: the texture, its overlay over it, each multiplied by its colour (a leather helmet's dye, a spawn egg's colours). Every version minecraft-assets has is there, also those the viewer has no world for (0.14, 0.15, 1.0): the server serves the export itself. What may be wrong is marked: an item with no icon, a texture the export lacks, an icon the game dyes that nothing colours (its dyed part grey, what the dye leaves alone faint), and, to look at, block icons all grey (the game colours some, leaves and grass, most it does not). "check every version" lists all of that for every version at once; so does `node examples/bedrock_preview/itemCheck.js [versions...]`. `items.html?version=1.26.51&filter=leather&show=problems`

They build their worlds in the page, with minecraft-data of the chosen version only.

```bash
npm install                  # in the repository: builds the viewer and its assets into public/
npx webpack -c examples/bedrock_preview/webpack.config.js
node examples/bedrock_preview/server.js
```

Then open http://localhost:3000/. A page takes the version to show from its address too: `blocks.html?version=bedrock_1.21.130`.

### Gameplay

`gameplay.html` is Bedrock's game loop with nothing outside the page: the server is `src/gameplayServer.js` in a Web Worker (`src/gameplay/server`), the client `src/gameplay/client` on the page, and between them a MessagePort carries what RakNet would: each turn's packets as one of the game's batches (each packet's length before it, with bedrock-protocol's `Framer`; no encryption, compression or Xbox sign-in). Every packet is written and read as bedrock-protocol writes and reads it: the version's protocol of minecraft-data compiled with bedrock-protocol's datatypes, and completed from the version's schema (`src/gameplay/protocol/schema.js`), so that the server and the client name what they mean once for every version, from 1.16.201 on: where a version has a field of its own, its schema's default fills it.

* The join is the game's: network settings (from 1.19.30), the login (read, not verified), the resource packs, `start_game` (and `item_registry` from 1.21.60), the chunk radius, the world, `player_spawn`.
* The world is the showcase of `world.html` (`src/showcase.js`) on plain ground that goes on; the server streams the columns around the player as it moves, as each version sends them: sections in `level_chunk` before 1.18, asked for with `subchunk_request` since. With the blob cache, a section or the biomes go as the hash of a blob the client may have already; the page keeps the client's blobs from one join to the next, so joining again misses none (the stats count them).
* Hashed block ids (from 1.19.80): the server names block states by their hashes in `start_game` and in every column; the client's registry, the viewer's and the physics read them so.
* The player moves with prismarine-physics' Bedrock engine (its `bedrock-web-viewer` branch): the client steps it every tick from the keys and the look and sends `player_auth_input`; the server's teleports (`move_player`) go through the engine's session.
* Building: in creative, the left button breaks the block aimed at at once and the right one places the hotbar's block against it (or opens or shuts a fence gate, unless the player sneaks); the client changes the block first, sends the item use (`inventory_transaction`), and the server's `update_block` confirms or puts it back. The hotbar holds building blocks the version has (the inventory the server sends), drawn with the version's item icons.
* The player starts wearing an elytra, with firework rockets and a boat in the hotbar's last two slots and another on the pond near the spawn (the water nearest it in a recorded world); the bar's game mode control switches creative, survival, adventure and spectator (`/gamemode`).
* Commands: `/setblock`, `/fill`, `/tp`, `/dimension`, `/gamemode`, `/time`, `/give`, `/replaceitem` (the hotbar and the armour: `/replaceitem entity @s slot.armor.chest 0 elytra`), `/help` (`~` for coordinates relative to the player).
* Items: right-click aiming at no block uses the held item; a firework rocket boosts a glide (an elytra worn, a jump in the air). A boat right-clicked onto water is put on it; right-click the boat to get in (the engine paddles it as the game's client predicts it: forward, left and right), sneak to get out, left-click it to break it (its item back out of creative).
* Views, as bedrock-demo's 3D view has them (`src/gameplay/view`): first person; third person, the camera 4 blocks behind the player as close as the blocks between leave room for (Bedrock's camera avoidance: eight rays from around the eyes), the version's player model drawn; and the walk view, a camera the right mouse button turns around the player (Ctrl+wheel: closer or further), where a click on the world walks the player there. In first and third person a click locks the mouse (raw movement where the browser has it), Escape lets it go, V (F5 while locked) switches between them.
* The pathfinder (`src/gameplay/pathfinder`, bedrock-demo's `bedrock-client-pathfinder` in the page): mineflayer-pathfinder as it is, on a bot made of the client, trying its moves with the same Bedrock engine (its `PlayerState` from the physics fork: the bundle points `prismarine-physics` there). It steers with the client's keys and look after each tick, as a person would with Human-like on (the look eases toward the way, eyes on the route ahead, walking once it faces the way), breaks the blocks in the way, places hotbar blocks to bridge or pillar up, jumps gaps and opens gates, as the Pathfinder menu allows (kept in the browser); a key or Escape stops it. Its route is drawn as bedrock-demo draws it: the way on the ground (cyan, amber where it goes only as near as found), each jump, gap or drop along the path Bedrock's jump flies (magenta) with boxes where it leaves the ground and lands, and boxes round the blocks it breaks (red), places (blue) and opens (orange), and the goal's.

Click the world to take the mouse (first and third person): WASD move, Space jumps (twice: flies, in creative), Shift sneaks, R or Ctrl sprints, the wheel and 1-9 pick a slot, T or / opens the chat, F3 the debug screen, Escape lets the mouse go. `gameplay.html?version=bedrock_1.26.51&cache=1&hashes=1&view=third` (`view`: first, third or walk; `&verify=1`: each packet read is written back and compared).

It needs, besides the pages' build, bedrock-protocol and prismarine-physics as `package.json` names them (`mc-zuri/bedrock-protocol` and `mc-zuri/prismarine-physics`, their `bedrock-web-viewer` branches; the physics as `prismarine-physics-bedrock`, so that mineflayer keeps its own), and mineflayer-pathfinder (`mc-zuri/mineflayer-pathfinder`, its `bedrock-web-viewer` branch: it runs in a page, timing its search with the global clock and without Node's `setImmediate`). The gameplay data adds to the viewer's the packets, the items, and the materials, enchantments and effects that prismarine-block's dig times read. `link-local.mjs`, one folder up, copies local checkouts of the three in their place. The bundles take the engine's TypeScript as it is (webpack strips the types: webpack 5.111, Node 22.6 or later), and are not minified (bedrock-protocol compiles some of its types from its own source). `--config-name gameplay --config-name gameplay-server` builds them alone (`--config-name replay-worker`: the replay's reader of recordings, built the same way).

#### Recorded worlds

Besides the showcase, the page plays worlds recorded from a Bedrock server (the World menu, `&world=<name>`), in every version it offers, whatever the version the world was saved by, and each of their dimensions: `&world=<name>:nether`, `<name>:end` (start_game names the dimension, and the chunks and their requests go in it; the sky is the dimension's colour). The world's portals take the player from one to another, as the game's do: a nether portal (after 4 seconds in it in survival, half a second in creative) between the overworld and the nether, to the portal there nearest the place 8 times nearer the origin (or farther from it), else to ground there; an end portal at once, from the overworld to the end's spawn and from the end back to the overworld's. The server sends `change_dimension` and streams the other dimension's columns; the client clears its own, and answers when `player_spawn` comes (the engine's dimension change, and `dimension_change_ack`). A portal takes a player who arrived in one only once they have stepped out of it. `/dimension <overworld|nether|end>` goes to a dimension's spawn. `worldImport.js` makes them from a world on disk: a LevelDB `db/` folder as Bedrock Dedicated Server keeps it, or as bedrock-demo's proxy saves what passes through it (with its `demo.json`: the version and the spawn):

```bash
NODE_PATH=../bedrock-demo/node_modules node examples/bedrock_preview/worldImport.js ../bedrock-demo/worlds/Explore --name explore
```

(It reads LevelDB with leveldb-zlib, a native module the viewer does not install: hence bedrock-demo's.) It writes `public/worlds/<name>.json` and `.bin` and lists the world in `public/worlds/index.json`, with the dimensions it has (the overworld, the nether, the end: each under its own keys in the world, as the game and bedrock-demo's proxy keep them), each with where a player starts: where the proxy saw it come in (`demo.json`), else a place to stand near the middle of its columns. Each block is kept by its name and states, and is worked out once for every version: the same block in its nearest state where the version has it; else what it was before Bedrock flattened its blocks (granite as `stone` with `stone_type=granite`, an oak log as `log` with `old_log_type=oak`), through Java's name for it (minecraft-data's `blocksB2J` of the world's version, then `blocksJ2B` of the version: 1.17.0's before 1.17); else a stand-in (deepslate's ores as the ores, anything solid as stone, the rest air). The import prints, for each version, how many of the world's states each way found. The biomes are read from each column's Data3D key, as the game writes them, and as bedrock-demo's proxy wrote them before it was fixed (see prismarine-chunk's `writeBiomes`); the page has one a column of blocks, the one of its highest block. A version before 1.18 has no blocks under y 0: the world's deepslate is cut off there.

`node examples/bedrock_preview/gameplayCheck.js [versions...] [--cache on,off] [--hashes on,off] [--world <name>]` plays the server and the client against each other in Node (22.18 or later), for every version the page offers with the cache and hashed ids off and on: every packet of the version written and read back, the join, every column the same on both sides, a join again with the cache missing no blob, a walk, a block placed and broken, a glide with an elytra boosted by a firework rocket, a boat put on a lake, driven, left and broken, in the showcase five pathfinder walks (round a wall, breaking into a box, pillaring up onto a pillar, through a gate, up a stair sprinting without running into a block's side, across the pond in creative without flying, flying in creative over a pit and up onto a pillar, gliding with an elytra down from a tower, with firework rockets over flat ground and up onto a plateau, across a lake in a boat it puts on the water and picks up again, round a canal's bend by boat turning no more than the bend asks, across the pond in a boat floating on it, across a lake, down to its floor, along its floor, out of it and into it; in the explore world from the ocean onto the shore and up a cliff; each where the server has the player too and every tick as the pathfinder predicted it), the commands, and with a recorded world each of its portals there and back.

### On GitHub Pages

`.github/workflows/bedrock-preview-pages.yml` builds the pages on every push to the `bedrock-web-viewer` branch and deploys them to the repository's GitHub Pages (Settings, Pages, Source: GitHub Actions). It installs the forks `package.json` names (minecraft-data, minecraft-assets, prismarine-chunk, prismarine-block, prismarine-registry: their `bedrock-web-viewer` branches), builds the viewer's assets of the Bedrock versions, then the pages, and writes the site with `build-site.js`: the files the server serves, written out (the items page's files of the Bedrock export, and the check of every version). The index page lists what the site was built from (`build.json`, by `buildInfo.js`; the server works it out as it serves it): the viewer and each fork, with the repository, branch and commit of each, as owner/name#branch (the branch linked to GitHub), and the data checkouts nested in minecraft-data and minecraft-assets. A fork installed from GitHub has the commit npm's lockfile names; a checkout of its own (the viewer, the data forks) its own, and whether it had changes not committed; a fork `link-local.mjs` copied, that of the checkout it copied (noted in the copy's `.link-local.json`). The replay plays the recordings of `public/recordings` there (`build-site.js` lists them in `recordings/index.json`; `$RECORDINGS`: a directory of more to put in the site). The gameplay page needs no server: its own is in the page. (bedrock-protocol brings raknet-native, which the page never loads: `SKIP_BUILD` keeps its install from building it when its prebuilt binary does not load.)

npm cannot install minecraft-data and minecraft-assets from git with their data (a submodule each: npm downloads GitHub's archive of the commit, which has none), so the workflow installs without scripts, puts the forks with their data in their place, and then builds:

```bash
npm install --ignore-scripts
# node_modules/minecraft-data: mc-zuri/minecraft-data-node, with mc-zuri/minecraft-data in minecraft-data/ (npm run generate:data)
# node_modules/minecraft-assets: mc-zuri/node-minecraft-assets, with mc-zuri/minecraft-assets in minecraft-assets/
PRISMARINE_VIEWER_VERSIONS=bedrock SKIP_BUILD=1 npm rebuild && npm run prepare
npx webpack -c examples/bedrock_preview/webpack.config.js
node examples/bedrock_preview/build-site.js _site
```

The versions are those the viewer's assets are built for: the Bedrock versions minecraft-assets has assets of (see the main README).
